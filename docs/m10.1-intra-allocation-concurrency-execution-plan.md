# M10.1: Intra-allocation task concurrency

## Objective

Run many single-threaded scientific processes concurrently inside a small,
site-bounded number of Slurm allocations. A Shoal target can use eight one-node
workers with forty task slots each, providing 320 concurrent processes without
placing 320 jobs or array elements in Slurm's controller queue.

## Public contract

Target configuration version 4 adds the required
`execution.worker_pool.task_slots_per_worker` field. Versions 1 through 3 retain
their existing schemas and use one sequential task slot per worker. Scalable
plans for target v4 use plan schema version 5 and report worker count, slots per
worker, concurrent logical-task capacity, maximum lane depth, and effective
worker allocation resources.

## Planning

For `S` slots, Rundra computes the worker count as the minimum of the configured
worker limit, concurrent-job limit, scheduler array limit, `ceil(tasks / S)`,
`floor(max_active_tasks / S)`, and required lease count. The concurrent capacity
is `workers * S`; lane depth is `ceil(tasks / capacity)`.

Each slot requests the logical task's CPU count. Worker memory is logical task
memory multiplied by slots. Worker walltime is logical task walltime multiplied
by maximum lane depth. Multi-slot workers reject multi-node, multi-task, and GPU
logical resource requests rather than oversubscribing an allocation.

## Slurm execution

Each worker is one Slurm array element and one node allocation. Its batch script
starts one `srun` step with exactly the configured task count, tasks per node,
and CPUs per task. Every `SLURM_PROCID` is a deterministic lane; tasks assigned
to that lane run sequentially. Scientific nonzero exits are journaled and do not
stop later tasks in the lane.

Each lane atomically seals a private journal. After a successful `srun`, the
batch script merges lane journals into the existing worker journal. On worker
infrastructure failure, Rundra reconciles any sealed or temporary lane journals;
completed scientific tasks keep their actual outcome and missing tasks inherit
the worker failure. There is no hidden retry or fallback location.

## Delivery increments

1. Add strict target-v4 parsing and plan-v5 rendering while preserving v1-v3.
2. Carry worker and slot limits through portable orchestration requests.
3. Render one bounded `srun` step and deterministic per-lane manifests.
4. Reconcile partial lane journals and record scheduling metadata.
5. Add unit/integration coverage and update architectural and CLI documentation.

## Validation

Run the unit suite, Ruff checks, formatting check, mypy, JSON contract tests,
and the minimal local execution example. Real-cluster tests remain explicitly
gated and must verify allocation hostnames before any scientific computation.
