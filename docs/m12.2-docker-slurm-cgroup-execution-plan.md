# M12.2 - Docker Slurm cgroup validation

## Goal

Add an opt-in Docker system test that proves Slurm enforces a Task's memory
limit. Keep the existing rootless Rundra end-to-end harness as the portable
default and do not add the privileged test to normal CI.

## Design

1. Extend the existing Docker Slurm image with a compute-only cgroup namespace
   bootstrap in a separately tagged test layer.
2. Run one compute container with a private, writable cgroup-v2 namespace and
   Slurm's `task/cgroup` and `proctrack/cgroup` plugins enabled.
3. Preflight cgroup v2, the memory controller, and delegated cgroup write
   access before starting the cluster.
4. Submit a small successful control job, then launch a bounded memory-pressure
   experiment through `rundr run --json`. Require Rundra's durable Run record
   to report a failed Task and Slurm to report `OUT_OF_MEMORY` for Rundra's
   recorded scheduler ID.
5. Preserve Compose logs and Slurm state on failure. Document this test as a
   privileged, development-only check rather than a production deployment
   recipe.
6. Expose the test through a separate manual GitHub Actions workflow on a
   rootful cgroup-v2 runner. Keep it out of normal and scheduled CI, cache the
   base image independently, and upload diagnostics after failures.

## Acceptance criteria

- `tools/run_docker_slurm_cgroup_tests.sh` passes on a compatible Docker host.
- The memory-pressure job is submitted, waited for, reconciled, and retrieved
  through Rundra rather than direct scheduler commands.
- The ordinary Docker Slurm test remains rootless and unchanged.
- Unsupported hosts fail before cluster startup with an actionable cgroup
  capability message.
- The cgroup variant is manually invoked and is not part of default pytest or
  scheduled CI.
- The `docker-slurm-cgroup-system` workflow provides an explicit manual CI
  entry point and rejects rootless or cgroup-v1 runners before building the
  cluster.
