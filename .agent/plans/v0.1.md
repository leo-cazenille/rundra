# Rundra v0.1 implementation plan

Status: M0, M1, M1E, M2, M3, and M4 complete at their acceptance gates; M5.3 complete

Last updated: 2026-08-15

Authority: `docs/project_specs.md`, especially sections 5–22, 28–47, and 49–53

## Purpose and non-negotiable boundaries

This is the living, dependency-aware plan from the initial repository to the
v0.1 definition of done. It preserves these invariants throughout:

- `Run` is a logical framework object, never a scheduler job.
- `Task` is a logical execution, never a Slurm array index.
- experiment configuration contains portable scientific intent; target
  configuration contains site/backend details.
- every stochastic task has an explicit integer seed before planning and
  execution; the launch layer may generate and then persist that integer.
- local and remote execution use the same planner and orchestration service.
- each submitted Run uses a new isolated source snapshot; staging later Runs
  cannot mutate it.
- concrete Slurm, SSH, rsync, and Apptainer code depends on portable models and
  ports, never the reverse.
- human and JSON CLI renderers consume the same typed operation-result objects.
- normal tests use local or fake infrastructure; shoal tests are opt-in.
- no persistent remote daemon, speculative plugin framework, or second
  scheduler is part of v0.1.

  available optional provenance without inventing missing values.

### Current state after M1.2 (2026-08-15)

- `LocalStager` allocates collision-safe per-Run workspaces, copies current
  source plus the byte-exact effective config, and returns backend-neutral
  semantic paths for sealed and mutable areas.

  in-tree `.rundra` workspace from entering the snapshot. Source symlinks are
  dereferenced to keep the snapshot isolated from later target changes.

### Current state after M1.3 (2026-08-15)

- `ApptainerRuntime` validates and constructs immutable, shell-free `exec`

  read-write bind mounts, and an absolute container working directory.
- Experiment environment values travel through the runtime-native inherited
  environment prefix: `APPTAINERENV_` by default and `SINGULARITYENV_` for a

  destinations fail explicitly.
- Capability validation performs executable discovery without running a
  container or a version command. Container execution, orchestration, and the

### Current state after M1.4 (2026-08-15)

- `LocalTransport` executes immutable argv without a shell and captures exact
  command context, UTF-8 stdout/stderr, timestamps, and non-zero exit status.
  `LocalScheduler` synchronously executes exactly one `ExecutionUnit`, assigns
  an opaque native reference, and retains a terminal portable observation.
- `OrchestrationService` validates one prospective plan against its experiment,
  creates the durable record before capability checks, stages through `Stager`,
  builds through `ContainerRuntime`, submits through `Scheduler`, and persists
  each observed lifecycle phase through `RunStore`.
- The service records stdout/stderr as separate Task artifacts and treats the
  versioned RunRecord artifact collection as the manifest. It fetches requested
  partial output after non-zero exit and preserves computation success when
  retrieval independently fails.
- The application service is implemented, but no execution CLI, asynchronous
  local run, provenance collector, native runtime, or multi-Task execution has
  been added; those remain later milestones.

### Current state after M1.5 (2026-08-15)

- The CLI exposes synchronous one-seed `run` and persisted `status`, `list`,
  `logs`, `fetch`, and `inspect` operations. All useful results support
  version-1 JSON and human output from the same typed values.
- Lifecycle commands accept an explicit record directory. Status and inspection
  need no initiating process; logs resolve Task artifacts; local fetch is

- A reconciled failed experiment returns its Run result with exit code 2.

- `submit` returns structured `ASYNC_UNAVAILABLE`; no daemon, detached local

### Current state after M1.6 (2026-08-15)

- `OrchestrationService` depends on a provenance provider rather than Git and

### Current state after M5.1 (2026-08-15)

- Seed ranges have strict inclusive `START:STOP` semantics; singleton and
  negative ranges are supported, malformed/reversed ranges fail explicitly,
  duplicate seed sequences have a dedicated error, and requested order is
  preserved.
- Plans and Runs require stable contiguous ordinal Task IDs, unique seeds, and

- `StagedWorkspace.for_task` derives shared immutable source/config paths plus

  Existing single-Task execution remains unchanged.
- The existing RunRecord v1 ordered Task entries, Task-keyed exit codes, and
  Task-tagged artifacts losslessly cover M5.1; a checked multi-Task round trip
  proves this without inventing scheduler-array fields before M5.2.

### Current state after M5.2 (2026-08-15)

- Execution plans contain an ordered grouping partition. Multi-Task Slurm
  plans select one `slurm_array` group; single-Task Slurm and non-Slurm plans
  retain singleton `one_unit_per_task` groups.
- Array compatibility requires the M5.1 shared config invariant plus uniform
  resources. Plan construction rejects missing/reordered Tasks, invalid
  strategy/target combinations, and heterogeneous array work.
- Public plan JSON and human output expose the exact Task ID ↔ seed ↔ contiguous
  zero-based array-index mapping without inventing a Run or scheduler job ID.
- RunRecord v1 persists the mapping as immutable definition data, validates it
  against the Slurm target and ordered Tasks, and reads older v1 records with an
  empty additive mapping. No script, submission, or accounting behavior exists
  yet.

### Current state after M5.3 (2026-08-15)

- `SlurmArrayRequest` validates the explicit group/mapping, at least two Tasks,
  contiguous indices, unique seeds, uniform resources, a safe absolute manifest
  path, and an explicit positive site `MaxArraySize` before rendering.
- A deterministic POSIX-shell Task manifest dispatches one exact array index to
  a command serialized through the established hardened shell boundary.
  Hostile literals round trip without execution; no `eval` or nested `sh -c`
  appears.
- The separate sbatch renderer emits `--array=0-N`, the existing resource/native
  allowlist, and mandatory distinct `%A`/`%a` stdout/stderr paths. It contains
  no Task command, config, or seed payload and invokes only the quoted manifest.
- Multi-Task `SlurmScheduler.submit` fails before transport use. Manifest
  persistence, actual array submission, and per-Task reconciliation remain
  M5.4 work.

  |

  |
  v

  |

This retains the specified M0–M6 backend order while inserting M1E as a bounded
usability milestone before remote execution. Within M0, only interfaces
required by M1 are fixed. M1E resolves launch inputs before the existing pure
planner. M2 deliberately proves transport/staging separately before M3 adds
scheduler behavior. M4 supplies real-backend evidence before M5 commits to
array mapping and per-task reconciliation details.

This is intentionally smaller than one package per backend interface. Split an
adapter into a package only when its implementation becomes unwieldy. Test
fakes stay in `tests/fakes.py` unless a supported public testing API becomes a
real need. A backend registry, dynamic discovery, abstract base-class hierarchy,
generic storage-role ontology, and public Python API are premature.

## Minimum architecture and abstraction limits

### Domain models

v0.1 needs immutable or mutation-controlled typed values for:
`ExperimentSpec`, command template, container request, `ResourceRequest`,
`Target`, `Run`, `Task`, `Artifact`, `RunRecord`, identifiers, timestamps, and
portable states. Config content is opaque YAML data but its exact effective
bytes/content are copied into the run record. Domain types contain no backend
objects or Slurm/SSH terminology; explicit native resource options remain a
namespaced mapping at the portable boundary.

Extensibility required now: additive schema evolution via version fields,
multiple tasks per Run, backend-native metadata kept separately, and absent
optional provenance represented explicitly. Deferred: arbitrary parameter
axes, DAGs, lineage, structured scientific metrics, a universal resource
ontology, and user-defined domain plugins.

### Planning and orchestration

v0.1 needs a pure planner that expands config plus seed(s), validates target
capabilities, resolves workspace-relative paths, and produces an inspectable
`ExecutionPlan` containing logical `ExecutionUnit` values. The orchestration
service consumes that plan, advances durable lifecycle state, and calls ports in
the order validate → persist CREATED → stage → submit/execute → reconcile →
fetch. Planning performs no submission and should avoid filesystem mutation
apart from reading/validating inputs.

Extensibility required now: execution strategy and backend metadata are explicit
plan fields, so Slurm arrays can group units later without changing Tasks.
Deferred: general workflow graphs, retry policy frameworks, policy engines,
adaptive campaigns, packing strategies, and event buses.

### `Transport`

v0.1 needs `check()` and `run(command, cwd, env)` returning a typed
`CommandResult` (argv, exit code, stdout, stderr, and timing). `Command` is an
argv tuple; SSH is responsible for the unavoidable remote-shell serialization
and quoting. Local and SSH transports share the port.

Extensibility required now: callers cannot depend on SSH text or authentication
details. Deferred: streaming/interactive sessions, connection pools, SFTP,
jump-host modeling beyond normal OpenSSH configuration, and capability
negotiation protocols.

### `Scheduler`

v0.1 needs `submit(normalized unit/group)`, `query(job references)`,
`cancel(job references)`, and enough accounting/log metadata to reconcile exit
state. It accepts an execution description—not `ExperimentSpec`—and returns
typed scheduler references and observations with portable and native states.
Waiting is orchestration-level polling over `query`, keeping scheduler adapters
free of workflow policy. `LocalScheduler` and `SlurmScheduler` exercise the same
port.

The normalized submission is a nonempty `SchedulerGroup` of `SchedulerUnit`
values. Each unit contains only `TaskId`, `Command`, and `ResourceRequest`;
scientific seed/configuration remain planner and provenance concerns. A
submission returns one opaque scheduler reference plus an explicit nonempty
logical-Task-to-native-ID mapping. Observations preserve the portable and
native state separately, with optional exit code, timezone-aware accounting
timestamps, scalar native metadata, and a synchronous `CommandResult` when one
is directly available.

Extensibility required now: one Run may map to one or more scheduler references,
and many Tasks may map through an explicit backend mapping. Deferred until a
second real scheduler: a supposedly universal job-description language,
scheduler feature negotiation, queue/accounting normalization beyond required
fields, packed execution, and declaring the port stable.

### `Stager`

v0.1 needs operations that create a unique run workspace, copy the current
source tree and effective inputs into it, seal the source snapshot before
submission, and fetch requested outputs/metadata idempotently. Local and rsync
implementations return typed workspace/artifact information. The port expresses
semantic paths needed by orchestration, not rsync flags or a universal storage
API.

Extensibility required now: local and remote path locations differ, and fetch is
separate from computation state. Deferred: Globus/object storage, content
addressing, deduplication, retention policy, generalized `$HOME`/`$SCRATCH`
roles, and `SharedFilesystemStager` unless shoal implementation proves it removes
real duplication.

### `ContainerRuntime`

v0.1 needs validation and pure argv construction from a normalized application
command, image, GPU flag, binds, environment, and workspace paths. Apptainer
owns `--nv` and bind syntax; Slurm never constructs container arguments. A tiny
native/no-container implementation may be used only if M1 confirms the
specification's “local/container execution” requires CI without Apptainer; it
must implement the same port and not become a bypass around orchestration.

Extensibility required now: runtime selection belongs to the target and runtime
metadata is preserved. Deferred: image building/pulling, digest caches,
Singularity as a separate adapter, Docker/OCI abstraction, and runtime plugins.

### Persistence

v0.1 needs a `RunStore`-shaped boundary with create, load, update, and list over
one schema-versioned JSON record per Run under a configurable user data root.
Writes use a temporary file in the same directory, flush/fsync as justified,
then `os.replace`; creation must fail on ID collision. Immutable snapshot/input
areas are separated from explicitly mutable runtime, output, logs, and metadata
locations. Retrieval outcome is recorded independently of computation outcome.

Extensibility required now: orchestration depends on store behavior, not path
layout, and unknown schema versions fail explicitly. Deferred: relational or
distributed databases, migrations before a second schema, distributed locks,
event sourcing, and multi-host writers. Evidence from concurrency tests will
decide whether a small local lock is needed.

### CLI and structured output

v0.1 needs the specified commands and `--json` on every useful operation.
Handlers call application services and receive typed result/error objects;
human and JSON renderers are the only divergent paths. JSON objects carry a
format/schema version, stable identifiers/states/error codes, deterministic
keys/collection ordering where relevant, and appropriate process exit codes.

Extensibility required now: the application service is independent from
`argparse` so a future Python/MCP/REST adapter can reuse it. Deferred: MCP,
REST, a stable public Python SDK, shell completion, rich terminal UI, and generic
command plugin discovery.

## Cross-milestone testing strategy

Testing is an architectural constraint:

- `FakeTransport` records argv/cwd/env and scripts connectivity/command results.
- `FakeScheduler` scripts observation sequences such as
  SUBMITTED→QUEUED→RUNNING→SUCCEEDED, RUNNING→FAILED, timeouts, and cancellation;
  it returns native metadata without scheduler prose leaking upward.
- `FakeStager` records unique workspace/source/input/fetch operations and can
  fail each phase independently.
- A recording runtime captures normalized input and returns known argv.
- Contract tests specify each port's observable behavior and run against fakes;
  local adapters also run applicable contracts. Concrete remote adapters use
  command generation/parsing tests plus fake executable/transport integration.
- State-transition tests cover valid/invalid paths and keep retrieval status
  independent. M5 adds deterministic aggregate-state tables.
- RunRecord tests round-trip every known/unknown/optional field, reject future
  incompatible versions, and simulate interrupted writes.
- CLI tests invoke the entry point, parse JSON rather than matching prose, and
  assert schema, stdout/stderr separation, deterministic ordering, and exit code.
- System tests carry a dedicated `system`/`shoal` marker and explicit opt-in;
  ordinary CI selects them out and performs no network or Slurm calls.

Every remote bug found in M4/M5 must first gain a default-CI regression fixture
when it can be reproduced without the cluster.

## Highest-risk areas

1. Safe SSH and sbatch shell serialization: argv cannot cross those boundaries
   directly, so quoting/path/native-option validation needs focused adversarial
   tests and one ownership point per format.
2. Durable asynchronous reconciliation: `squeue` disappearance, delayed/absent
   `sacct`, cancellation races, and retrieval failures must not corrupt the
   portable state or lose scheduler references.
3. Snapshot immutability and provenance: rsync must capture dirty/non-Git trees
   into a Run-specific location, handle partial transfers, and avoid symlink/path
   escape while keeping logs/output writable.
4. Slurm array accounting: explicit Task/seed/index mapping, mixed terminal
   states, per-task logs, and site/version-specific accounting formats require
   real M4 evidence before M5 finalization.
5. Public contract timing: JSON/schema choices become expensive to change, so
   M0 documents only necessary envelopes and M6 freezes exact v0.1 fields after
   both execution paths work.
6. Real-environment validation: CPU/GPU acceptance depends on authorized shoal
   access, valid image/resources, and cluster availability; never substitute a
   fake test for recorded system evidence.

## Ambiguities and specification tensions to resolve incrementally

- M1 requires both “Apptainer runtime” and a minimal local example, while the
  broader local scenario says “local/container execution.” It is unclear whether
  local execution without Apptainer is required. Decide schema/behavior in M1;
  keep any native runtime tiny and on the common port.
- v0.1 requires asynchronous Runs and all CLI commands, but does not explicitly
  state whether `submit` must work for the local target. Remote/Slurm async is
  mandatory; local async should be capability-rejected or implemented only with
  sound post-process semantics.
- “Run directories immutable once execution begins” coexists with runtime
  state/output/log writes. The plan interprets this as immutable source/input
  and explicitly mutable runtime/output/log/metadata subtrees, matching
  `AGENTS.md`.
- The specification lists a portable `Target` domain concept while demanding
  target/site separation. The plan treats `Target` as portable configuration
  composition data with backend-specific config values, never scientific
  experiment content.
- `UNKNOWN` is listed as a portable Run state but transition/aggregation rules
  are unspecified. M0 defines conservative transitions; M5 finalizes aggregate
  precedence from real scheduler behavior.
- The specification suggests versions “where appropriate” but public JSON
  examples omit a format version. M0 should add/document one consistently or
  explicitly document why the envelope is versioned elsewhere; this is a
  specification clarification, not a silent change.
- The spec requires source/container identity “when practical.” M1 should record
  unavailable values explicitly; M4 supplies evidence for checksum cost and
  whether caching is justified.

No direct conflict between `AGENTS.md` and `docs/project_specs.md` was found.
`AGENTS.md` reinforces the same boundaries and adds the explicit rule that only
designated runtime/output locations may change after execution starts.
